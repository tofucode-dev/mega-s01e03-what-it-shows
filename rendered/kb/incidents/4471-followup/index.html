Parser: tenant dates read month first

The shared parser expects month first even when the tenant’s locale is day first. Use the tenant directory and Intl.DateTimeFormat(...).formatToParts(...), not the reporter’s browser locale. For example, R-41203 reports “Booked for 2 December. The invite says 12 February.” With a day-first tenant, interpreting 02/12/2026 as month/day produces that reversal.

Fix the shared parser’s explicit date contract. Test app, email and booking-v2 paths with ambiguous dates, unambiguous days above twelve, leap days, and invalid dates. Keep date-only values distinct from timestamps. This is a proposed fix and test plan, not a verified product reproduction.

Form hint: booking-v3 invites the wrong input

For day-first tenants using booking-v3, the form prints MM/DD/YYYY, while the form reads dates in the tenant’s order. Users following that hint supply month-first input to a day-first form. This differs from the shared parser defect. R-41241 is a form report from alder.physio (de-DE, booking-v3) whose browser says en-US; classify by tenant and form, not the browser or intake tag.

Make the hint, validation, parser and saved value agree with the tenant’s date contract. Test booking-v2 against booking-v3, form against app/email, and browsers whose locale differs from the tenant. Correcting only the shared parser does not correct a misleading hint.

One-day shifts: preserve uncertainty

Collect the intended local date, original input, tenant timezone, UTC payload, invite/reminder timestamps, client display timezone and booking creation time for each date-shift report. Compare Lisbon and Toronto views of the same invite; check daylight-saving boundaries without assuming they are the cause.

Premature invite: separate from date shifts

R-41236 says the invite arrived before booking creation. This does not report a one-day date shift, so it has its own issue rather than inheriting that investigation’s cause or fix. It lacks the timestamps needed to establish whether the invite actually preceded its booking. Collect booking creation and invite generation/delivery timestamps, booking identity and audit records; check ordering, retries and correlation IDs. No specific scheduler or clock defect is proven. Do not discard a report simply because the current classifier has no category for its symptom.

Queue history

The chart computes received and merged weeks independently. A batch merge is not a batch of newly received reports. The current export cannot tell us which new reports arrived after it was made.

Triage from now on

Subject equality is not causal equality. The old triage page is stale under its own layout’s age check, and decision 0001 remains an immutable historical record. See the proposed replacement; it is not accepted policy yet.

Read the body first. Resolve tenant locale and booking-form version, then identify channel and mechanism. Different subjects can share a cause; identical subjects can conceal different bugs. With an unknown tenant or contradictory symptoms, keep the report for manual investigation. Never merge two unknowns as though “no cause” meant “same cause”. Count distinct report IDs only, retain original timestamps, and refresh from the desk’s next export before using these counts as current. Close each ticket with its actual recorded outcome: completed for the reported parser fix, not planned for the retired booking-v3 hint. Never treat a shared “closed” state as proof that every problem was fixed.
